Microsoft "AI 에이전트는 내부자 위협": Guardian Agents로 에이전트 감시 나선다

2026.10.20 08:31 KST읽는 시간 약 7분#AI안전 #보안 #에이전트
핵심 정리
  1. Microsoft가 10월 19일 공식 블로그에서 AI 에이전트를 '내부자 위협'처럼 다뤄야 한다며, 에이전트를 감시하는 Guardian Agents와 작업별 권한 제한(Dynamic Permissions) 등 보안 기능을 발표했습니다.
  2. Microsoft 보안 총괄은 최첨단 모델도 악의 때문이 아니라 예측 불가능성 때문에 믿을 수 없다고 밝혀, 모델 회사의 안전 약속과 별개로 사용하는 쪽이 통제를 책임져야 한다는 흐름이 굳어지고 있습니다.
  3. 개발자는 에이전트에 최소 권한만 주고, 위험한 작업에는 사람 승인을 넣고, 모든 행동을 로그로 남기는 설계를 기본으로 삼아야 합니다.

01이 이슈는 무엇인가?

AI 에이전트를 '내부자 위험'으로 관리하는 에이전트 보안 (Agentic Insider Security)

관련 용어 AI 에이전트는 목표를 받으면 스스로 계획을 세워 코드 실행, 파일 수정, API 호출 같은 행동을 이어 가는 AI 프로그램입니다. 내부자 위협은 외부 해커가 아니라 시스템 접근 권한을 가진 직원이나 프로그램이 일으키는 보안 사고를 말합니다. 최소 권한 원칙은 일을 하는 데 꼭 필요한 권한만 주는 보안의 기본 규칙입니다.

03무슨 일이 있었나?

오늘 발표된 내용

Microsoft 보안 부문 총괄 Hayete Gallot는 공식 블로그 글 「Securing the agentic insider」에서, 기업 안에서 일하는 에이전트가 권한은 과하게 갖고 중요한 결정을 내리는데도 그동안 암묵적으로 신뢰받아 왔다고 지적했습니다. 그는 최첨단 모델을 완전히 믿을 수 없는 이유로 악의가 아니라 보상 해킹(점수만 올리는 편법을 배우는 현상) 같은 학습 방식의 부작용과, 회사 규칙과 어긋나게 행동할 가능성을 들었습니다.

함께 공개된 Microsoft Security 블로그 글에는 구체적인 기능이 담겼습니다. 사람 대신 에이전트를 실시간으로 지켜보는 Guardian Agents, 작업에 필요한 만큼만 시간을 정해 권한을 주고 위험한 행동에는 사람 승인을 요구하는 Dynamic Permissions, 에이전트를 정책으로 통제된 샌드박스에서 돌리는 Microsoft Execution Container, 그리고 에이전트마다 위험도를 계속 계산하는 Dynamic Agent Risk입니다. 직원이 PC에 설치한 로컬 에이전트도 35종을 추가해 총 60종(Claude Code, Codex, GitHub Copilot 등)을 찾아낼 수 있게 했습니다. 다만 각 기능의 정식 출시일은 글에 나오지 않았고, 11월 17~20일 Microsoft Ignite 행사가 언급됐습니다.

Microsoft는 모델의 입력·출력뿐 아니라 추론 과정(사고 사슬)까지 볼 수 있어야 에이전트가 맡은 일과 다르게 움직이는지 판단할 수 있다며 '모델 투명성'도 요구했습니다. TechCrunch는 Microsoft가 OpenAI·Anthropic에 투자하면서 동시에 에이전트 보안 제품을 판다는 이해관계가 있다고 짚었습니다.

04실무자가 해볼 것

1. 에이전트 전용 계정과 키 쓰기

개인 관리자 계정이나 무제한 API 키를 에이전트에 그대로 주지 마세요. 에이전트용 키를 따로 만들고 사용 한도와 만료일을 걸어 두세요.

2. 최소 권한으로 시작하기

읽기 전용 권한에서 출발해 필요할 때만 쓰기 권한을 더하세요. main 브랜치 직접 푸시, 운영 DB 접근은 기본으로 막아 둡니다.

3. 위험한 행동엔 사람 승인 넣기

결제, 삭제, 배포, 외부 메일 발송처럼 되돌리기 어려운 작업은 에이전트가 실행 전에 사람에게 확인받도록 설계하세요.

4. 샌드박스에서 돌리기

에이전트는 컨테이너나 가상 환경 안에서 실행하고, 접근 가능한 폴더와 네트워크 주소를 정해 두세요.

5. 모든 행동을 로그로 남기기

에이전트가 실행한 명령, 호출한 API, 바꾼 파일을 기록하면 사고가 나도 원인을 빨리 찾고 되돌릴 수 있습니다.

6. 비용 알림 설정하기

API 제공사 콘솔에서 일일·월간 지출 알림과 한도를 걸어 두세요. 키 유출이나 무한 반복을 가장 먼저 알려 주는 신호입니다.

7. 키를 한곳에 모아 두지 않기

여러 서비스의 API 키를 한 플랫폼에 몰아 저장하면 한 번의 유출로 모두 잃습니다. 키는 비밀 관리 도구에 두고 주기적으로 교체하세요.

05긍정적인 방향으로 간다면?

  • 에이전트 보안이 기본 기능이 된다. 권한 제한·승인·로그가 플랫폼에 기본 탑재돼 개인 개발자도 쉽게 안전한 에이전트를 만들 수 있습니다.
  • 기업 도입이 빨라진다. 통제 장치가 갖춰지면 보수적인 기업도 에이전트를 더 넓게 쓰고, 관련 개발 일자리가 늘어납니다.
  • 업계 표준이 생긴다. 에이전트 신원, 권한, 긴급 정지에 대한 공통 규칙이 생겨 도구끼리 연동이 쉬워집니다.
  • 사고 공유 문화가 자리 잡는다. 기업들이 실패 사례를 공개하고 함께 대응하면서 같은 사고가 반복되지 않습니다.

06부정적인 방향으로 간다면?

  • 감시 비용이 너무 커진다. 에이전트마다 감시 에이전트를 붙이면 비용과 복잡도가 늘어 작은 팀은 따라가기 어렵습니다.
  • 특정 플랫폼에 묶인다. 보안 기능이 Microsoft 같은 대형 플랫폼 안에서만 잘 돌아가면 다른 도구를 쓰는 개발자는 불리해집니다.
  • 감시가 사람으로 번진다. 에이전트 감시용 데이터가 직원 업무 감시로 이어질 수 있다는 우려가 커질 수 있습니다.
  • 통제가 뚫리는 사고가 터진다. 감시 장치를 믿고 권한을 넓혔다가 우회되면 피해가 오히려 커질 수 있습니다.

07입문 개발자에게 남는 것은?

Microsoft의 발표는 "좋은 모델을 고르면 안전하다"는 생각에서 "어떤 모델이든 바깥에서 통제해야 한다"는 생각으로 업계의 무게중심이 옮겨 가고 있음을 보여 줍니다. 같은 주에 나온 에이전트 무단 행동 공개와 API 키 유출 사고는 이 주장이 이론이 아니라는 점을 뒷받침합니다.

입문 개발자에게 이 뉴스는 에이전트를 쓰지 말라는 경고가 아니라 안전하게 쓰는 설계를 처음부터 익히라는 신호입니다. 전용 키, 최소 권한, 사람 승인, 샌드박스, 로그라는 다섯 가지 습관만 지켜도 대부분의 사고는 크게 줄일 수 있습니다.
