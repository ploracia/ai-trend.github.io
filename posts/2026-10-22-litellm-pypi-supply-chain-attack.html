01이 이슈는 무엇인가?

LiteLLM 1.107.0 소프트웨어 공급망 공격: AI 개발 환경의 자격 증명을 노린 악성 패키지

관련 용어 공급망 공격은 내가 직접 해킹당하는 대신, 내가 믿고 내려받는 라이브러리나 도구에 악성 코드를 심어 퍼뜨리는 공격입니다. PyPI는 pip install로 받는 파이썬 패키지 저장소입니다. wheel은 미리 빌드된 파이썬 설치 파일 형식입니다. .pth 파일은 파이썬이 시작될 때 자동으로 읽는 설정 파일로, 악용하면 import하지 않아도 코드가 실행됩니다. 자격 증명(credential)은 API 키, 비밀번호, 토큰처럼 시스템 접근 권한을 증명하는 정보입니다.

03무슨 일이 있었나?

오늘 발표된 내용

Chainguard 분석에 따르면 LiteLLM 1.107.0은 10월 21일 11시 39분(UTC, 한국 시간 20시 39분) PyPI에 올라왔고, 7개 wheel 모두에 악성 코드가 들어 있었습니다. Docker Hub의 latest 등 여러 태그와 GitHub 컨테이너 이미지도 같은 버전으로 오염됐습니다. GitHub 소스 코드와 태그 자체는 깨끗했기 때문에, 코드를 보고는 알기 어려웠습니다. StepSecurity에 따르면 해당 버전은 같은 날 13시(UTC) 무렵 PyPI에서 내려갔습니다.

악성 wheel은 site-packages에 cook.pth, cook.py, sitecustomize.py 세 파일을 넣습니다. 이 파일들은 LiteLLM을 import하지 않아도 파이썬이 시작될 때마다 실행됩니다. 첫 번째 동작은 정보 탈취로, SSH·GPG·TLS 개인 키, 클라우드·쿠버네티스 자격 증명, CI/CD 비밀값, 브라우저 저장 정보, 환경 변수, 20개가 넘는 AI 코딩 도구의 설정, 그리고 LiteLLM 프록시 데이터베이스에 저장된 LLM 제공사 API 키까지 모아 암호화한 뒤 진짜와 비슷한 litellm[.]dev 도메인으로 보냈습니다. 두 번째는 리눅스·macOS에서 매시간 GitHub의 특정 파일을 확인해 공격자가 지정한 코드를 내려받아 실행하는 백도어입니다(분석 시점에는 아직 비어 있었다고 함).

The Hacker News에 따르면 LiteLLM 보안 책임자는 엔지니어 3명의 GitHub 계정이 탈취된 GitHub CLI 토큰으로 쓰였고, 한 계정이 릴리스를 만들고 다른 계정이 승인했다고 밝혔습니다. 회사는 관련 토큰을 모두 폐기하고 레지스트리의 '신뢰할 수 있는 게시(trusted publishing)' 연결도 임시로 끊었습니다. 안전한 최신 버전은 1.106.2이며, 1.107.0 릴리스 후보(rc1, rc2)는 깨끗한 것으로 분석됐습니다.

04실무자가 해볼 것

1. 지금 바로 1.107.0 설치 흔적 찾기

requirements.txt, poetry.lock, uv.lock 등에서 litellm 버전을 확인하고, site-packages에 cook.pth나 sitecustomize.py가 있는지 셸 명령으로 찾아보세요. 감염 의심 환경에서는 파이썬을 실행하지 않는 것이 좋습니다.

2. 설치됐다면 키를 전부 교체하기

그 컴퓨터나 CI에서 접근할 수 있던 클라우드 키, SSH 키, GitHub 토큰, OpenAI·Anthropic 등 LLM API 키를 깨끗한 환경에서 새로 발급하세요. LiteLLM 프록시를 썼다면 마스터 키와 저장된 제공사 키도 바꿔야 합니다.

3. litellm==1.106.2로 고정하기

litellm>=처럼 열어 둔 버전 조건은 배포 시간대에 악성 버전을 받았을 수 있습니다. 정확한 버전으로 고정하세요.

4. 해시 검증과 lockfile 습관 들이기

pip install --require-hashes나 uv·poetry의 lockfile을 쓰면 같은 버전이라도 파일이 바뀌었을 때 설치가 막힙니다.

5. Docker 이미지는 태그 대신 digest로

latest 태그는 언제든 다른 이미지를 가리킬 수 있습니다. 운영 환경에서는 image@sha256:... 형식으로 고정하세요.

6. 새 버전 '숙성 기간' 두기

공개된 지 며칠 안 된 패키지는 자동 업데이트하지 않도록 의존성 봇이나 사설 저장소 설정을 바꾸세요. 이번 악성 버전은 약 1~2시간 만에 내려갔습니다.

7. 개발 PC와 비밀 정보를 분리하기

API 키를 셸 환경 변수나 평문 파일에 두지 말고 비밀 관리 도구를 쓰세요. AI 코딩 도구 설정 파일에 저장된 토큰도 탈취 대상이었습니다.

05긍정적인 방향으로 간다면?

  • 빠른 탐지 체계가 효과를 증명한다. 공개 16분 만에 스캐너가 잡아낸 사례가 알려지면서 패키지 자동 검사가 더 널리 쓰일 수 있습니다.
  • 배포 출처 증명이 표준이 된다. 이번 wheel에는 출처 증명(provenance)이 없었다는 지적이 나와, 서명·증명 없는 릴리스를 막는 관행이 퍼질 수 있습니다.
  • AI 개발자의 보안 감각이 높아진다. 버전 고정, 해시 검증, 키 분리 같은 기본 습관이 AI 프로젝트에도 자리 잡을 계기가 됩니다.
  • 오픈소스 관리 권한이 정비된다. 릴리스 권한을 가진 계정과 토큰 관리가 엄격해지며 유사 사고가 줄어들 수 있습니다.

06부정적인 방향으로 간다면?

  • AI 도구가 주요 공격 표적이 된다. LLM API 키와 AI 코딩 도구 설정이 돈이 되는 정보가 되면서 비슷한 공격이 계속될 수 있습니다.
  • 2차 피해가 뒤늦게 드러난다. 이미 빠져나간 키로 클라우드 요금 폭탄이나 추가 침입이 몇 주 뒤에 발생할 수 있습니다.
  • 오픈소스 신뢰가 흔들린다. 같은 프로젝트가 반년 사이 두 번 공격받으면서 기업이 오픈소스 도입을 꺼리게 될 수 있습니다.
  • 유지보수자 부담이 더 커진다. 보안 요구가 늘어나지만 이를 감당할 인력과 자금이 부족한 프로젝트가 많습니다.

07입문 개발자에게 남는 것은?

이번 사건은 AI 앱의 보안이 프롬프트나 모델만의 문제가 아니라는 점을 보여 줍니다. 공격자는 모델이 아니라 개발자가 매일 쓰는 pip install을 노렸고, 그 결과 LLM API 키와 클라우드 권한을 한꺼번에 가져가려 했습니다.

입문 개발자에게 가장 중요한 교훈은 세 가지입니다. 버전을 고정하고, 키는 코드와 분리하고, 의심되면 바로 교체한다. 이 기본기만 지켜도 이런 사고가 일어났을 때 피해를 크게 줄일 수 있습니다.
